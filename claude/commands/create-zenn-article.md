# Create Zenn Article from Current Workspace

現在のワークスペースを分析し、Zenn記事の下書き（Markdown）を書く。

読者にとっての価値は「実際に何が起きたか」にある。ここで最も避けたいのは、体裁を埋めるために起きていない問題や動かしていないコードを書いてしまうことなので、以下の原則を手順より優先する。

## 原則

- **書くのは実際に確認したことだけ。** エラーメッセージ、ログ、計測値、バージョン番号は、実ファイルや実行結果から引用する。記憶や推測で書かない。確認できないことは書かずに、ユーザーに「ここは事実確認が必要」と伝える。
- **コードブロックは実ファイルからの引用。** 長い場合は抜粋・省略（`// ...`）してよいが、書き換えない。実在しないAPIやオプションを補わない。
- **秘密情報（APIキー、認証情報、社内固有の識別子）は含めない。**
- 日本語で書く。技術用語は英語のままでよい。

## 手順

### 1. ワークスペースを分析する

- README.md、docs/ 配下、CLAUDE.md、TODO.md などのドキュメント
- package.json、compose.yaml などの設定ファイル（技術スタックとバージョンの確認）
- 主要な実装ファイル
- 可能なら git log — 「なぜこう書いたか」「何に詰まったか」は履歴に残っていることが多く、記事の核になる

### 2. 構成案を提示して合意を取る

本文を書く前に、タイトル案（2〜3個）と見出しの並びを短く提示し、ユーザーに確認してもらう。

切り口はプロジェクトを作った本人にしか決められない。全文を書いてから方向性が違うと分かると全部やり直しになるため、ここで合意しておく。

### 3. 本文を書く

下の構成は**メニューであって、穴埋めフォームではない**。そのプロジェクトに該当する節だけを使い、当てはまらない節は見出しごと落とす。特に「遭遇した問題」は、実際に詰まった記録が無いなら書かない。

- **はじめに** — 背景・課題、なぜ作ったか、この記事で分かること
- **技術スタック・環境** — 使った技術とバージョン、前提条件
- **実装のポイント** — コード引用と、なぜその方法を選んだかの説明
- **遭遇した問題と解決法** — 症状（実際のエラー出力）／原因／解決策。実例がある場合のみ
- **デモ・動作確認** — 読者が再現できるセットアップ手順と実行コマンド
- **まとめ** — 成果と、今後の改善点
- **参考リンク** — リポジトリURL、参照したドキュメント

見出しは `##`（h2）から始める。`#` は記事タイトルとして自動で描画されるため、本文で使うと重複する。

図やスクリーンショットがあると伝わる箇所は、自分で作らずに「ここに図があるとよい」と指摘する。

書ける材料が足りないと判断したら、無理に埋めずにそこで止まる。何が足りないか（動作確認のログ、詰まった記録、比較対象）を伝える方が、薄い記事を渡すより有用。

### 4. 出力する

```yaml
---
title: "記事タイトル"
emoji: "🛠"
type: "tech"
topics: ["typescript", "docker"]
published: false
---
```

- `emoji` は1文字のみ
- `type` は `"tech"`（技術記事）か `"idea"`（アイデア・ポエム）のどちらか
- `topics` は最大5つ。使った技術名をそのまま小文字で書く（`typescript`, `docker` など）。確信の持てないタグで5つ埋めようとせず、少なくてよい
- `published` は `false`（下書き）
- `published_at` は書かない。一度設定すると変更できないため、公開時にユーザーが決める

出力先は `$ARGUMENTS` でパスが指定されていればそこ、無ければワークスペース内に書き出す。ファイル名は Zenn の slug 規則（英小文字・数字・`-`・`_` の12〜50文字）に合わせておくと、そのまま Zenn リポジトリの `articles/` に移せる。

### 5. 最後に伝える

- 生成したファイルのパス
- 事実確認が必要な箇所（あれば）
- 図やスクリーンショットを足すとよい箇所
